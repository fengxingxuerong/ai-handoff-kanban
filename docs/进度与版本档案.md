**2026-10-25（v1.9.6 附 18）：英文别名 + 工具标题双语 —— 把「任何 agent 都能接手」这句承诺补全。**
起因：横向看同类项目之后列了三条要补的，第 1 条是分发（附 16），这是第 2 条。
**问题**：契约以前**只收中文** —— MCP 的 `enum` 是 `["待办", …]`、HTTP 的 `Literal` 也一样。
英文 agent 传 `status: "in_progress"` / `priority: "high"` 会直接 422 / failed，
等于要求调用方懂中文。这是「任何 agent 都能接手」里唯一货不对板的地方 —— 而这条
在竞品矩阵里**看不见**（矩阵比的是功能有无，不是契约的语言中立性）。
**做法（两层各自归一，定义只有一处）**：
· 别名表 `FIELD_ALIASES` 与规范值白名单**同文件**（`app/fields.py`）—— 分家迟早漂；
  归一算法 trim + 小写 + `-`/空格折 `_`，所以 `In Progress` / `in-progress` 都命中；
  **不认识的值原样放行**，拒绝仍由 `Literal`/`enum` 给出（错误信息才具体）；
· HTTP 走 `field_validator(mode="before")` —— Pydantic 的 `Literal` 在 before **之后**才判，
  别名只能在这个位置生效；MCP 走 `_canonicalize_args()`，**在 `_validate_args` 之前**
  （校验器比的是 enum，别名要先变规范值再进那一关）；
· **一张扁平表**装四组（项目状态/任务状态/优先级/记忆类型），靠「规范值本身不冲突」成立

**2026-10-27（v1.9.6 附 21）：补上「我在哪块板上」—— 一条一直缺的反查。**

**缺口**：项目里早就存着 `repo_path`（雷达按它扫 git、按它算完成度），但**没有反向查询**。
一个在仓库里干活的编码代理没法回答"我该在哪块板上记这件事"，只能 `kanban_list_projects`
再靠人眼比对路径 —— 而"接手时先搞清楚自己在哪个项目"恰恰是这个工具存在的理由。

**做了什么**（一条实现、三处复用）：
· `repo_watch.match_project(projects, path)` 纯函数：**完全相同 → `exact`；落在仓库里面
  （含任意层子目录）→ `inside`；取最长的那条**（仓库套仓库时短路径不能吃掉长的）；
  **同样长 = 并列候选、不猜**（与 `find_project` 重名同口径）；
· `GET /api/repo-locate?path=`（本地只读）与 MCP 工具 `kanban_project_for_path`（read）
  **共用那一份判据**，不各写一套 —— 本项目反复出问题的形状就是两条路给不同答案；
· MCP 那份 `path` 可省：省了用**进程 cwd**。MCP 服务由客户端在项目目录里拉起，
  所以 cwd 往往正是调用方所在的仓库 —— 零参数问一句「我在哪块板上」才真的可用；
  HTTP 那份**必须给 path**：桌面应用的 cwd 是它自己启动的地方，拿它当"你所在的项目"
  会给出一个看着像答案的错答案。同一件事两处默认值不同，理由是各自的 cwd 含义不同。

**两个刻意的诚实性细节**：
① 目录归一化**只做字符串运算**（`abspath`+`normpath`+`normcase`，去引号）——
   不 `resolve` 符号链接、不测存在性：还没 clone 的目录也该能认出来，
   而"这个目录属于哪块板"不是"这个目录在不在"能回答的问题；
② 没匹配上时说清是**哪一种**「没有」：这个目录不属于任何项目 / 另有 N 个项目压根没填
   `repo_path` —— 否则"补一个路径就能认出来"会被读成"看板里没有这个项目"，用户永远想不到去补。

**验证**：6 条纯函数用例（exact/inside、最长优先、大小写与分隔符、并列候选、两种"没有"、
空 `repo_path` 不许匹配、Windows 盘根）+ HTTP 用例（端点三个分支 + 缺 path 400）

  仍是 pytest 的目录，断言却因为没断言到点上而"通过"）。改成进程内直接调处理器 + monkeypatch

**2026-10-25（v1.9.6 附 15）：检修轮 —— 抓到的是我上一轮刚加的护栏，它自己被 mock 骗过了。**
用户让「检修」，于是把上轮加的东西**逐条复验**（而不是相信当时那张全绿的表）。抓到两处：
**① 探针的运行护栏在 Windows 上判不出「那个进程还在不在」。** 护栏靠 `_pid_alive`，
而它用的是 `os.kill(pid, 0)` —— Windows 上那不是探测，CPython 把它实现成 `TerminateProcess`
（以退出码 0 结束那个进程），权限不足时抛 OSError。实测后果两条：同用户进程会被**杀掉**；
没权限时判「已死」→ 活进程当陈锁 → **第二份探针照常开跑**（退出码 0，而不是该有的 3）。
改用 `OpenProcess(SYNCHRONIZE)` + `WaitForSingleObject(h, 0)`，失败原因用 `GetLastError` 分辨
（不存在 vs 有但没权限 —— 后者按**活着**处理：宁可少跑一份探针，也不能两份同时改源码）。
**它为什么能藏住整整一轮**：那两条护栏用例都 monkeypatch 了 `_pid_alive`，从没碰过真实现 ——
正是本项目第 1 条纪律「拒绝 mock 自证」说的那件事。补了一条**只用真 PID** 的用例
（本进程=活 / 刚退出的子进程=死）。
**证据不是合成变异，而是一前一后的端到端实测**：修之前拿一份「活锁」去跑契约用例，
护栏**没拦住**（退出码 0，照常开跑）；修之后同一份活锁让它**拒绝开跑**并说出是谁在跑。
（旧的 `os.kill` 实现没法用执行式 A/B 验 —— 跑起来它把测试进程杀掉了，字面意义上的「护栏变凶器」。）
**② 我自己的 A/B 脚本中途死掉，把源码留在了变异态。** 那版脚本没有 `try/finally`，
异常退出时没还原；而那次修复还没提交，`git checkout` 也救不回来（只能手工修回）。
纪律与探针自己那条一样：**还原写在 finally 里**（外部信号杀进程时 finally 也走不到，
所以要靠「自愈」而不是「记得」）。
**顺带把「报告过的账」对了一遍**：我之前说「真实数据没被碰过（`mcp_readonly=false`）」，

**2026-10-25（v1.9.6 附 8）：探针的还原不是逐字节的 —— 行尾被悄悄翻译成 CRLF。**
第二批 JS 探针跑完之后，`git status` 里冒出 `web/js-ai.js` / `web/js-reality.js` 的 M，
而 `git diff` **是空的**、残留自检也是空的、mtime 是旧值（还原成功）。三条线索拼起来才看清：
`git ls-files --eol` 给出 `i/lf w/crlf` —— **索引里是 LF、工作区成了 CRLF**。
根因：`apply_and_run` 用 `Path.write_text` 还原，而它走**文本模式**，在 Windows 上把每个 `\n`
翻成 `\r\n`。于是「注入 → 还原」两遍写下来，**整份文件的行尾被改了** ——
内容读起来一模一样（`read_text` 相等、`git diff` 归一化后为空），但它**不是逐字节还原**，
而它自己的用例比的正是「文本 + mtime」，**根本抓不到**。
**修了两遍才对**（这一节本身值得记）：
  · 第一版改成 `write_text(..., newline="")` —— 只补了**写**侧。而 `read_text` 在**读**的时候
    就做了 universal newlines（CRLF→LF），于是反向污染：把 CRLF 文件写成 LF。
    实测证据：`ci_local` 跑完一轮，`git ls-files --eol` 里一批文件从 `w/crlf` 变成 `w/lf`。
  · 最终版：**`raw = read_bytes()` 进、`write_bytes(raw)` 出** —— 逐字节相等不再是「尽量做到」，
    而是构造上成立；变异表里的 LF 文本由 `_native()` 适配成文件自己的行尾（否则 CRLF 文件里
    匹配不上）。
钉子 `test_apply_and_run_restores_bytes_for_both_line_endings`：**两种行尾各一条**、比 `read_bytes`、
且 old/new 跨行（CRLF 那条必须真的走到 `_native` 才匹配得上）。A/B 把**当初真写过的两版**
各放回去一次（读文本+写文本 / 读文本+写文本(newline=)）→ 两次都**红**，还原逐字节同哈希。
（第一次 A/B 我把第二格设计成了「读字节 + newline=」，那其实**是对的**、与修法等价 ——
 缺陷的根在读侧，不在写侧；教训：A/B 要复现**真写过的那版**，不是复现一个看着像的版本。）
**把话说准一点**（我先说大了）：这**不是**「把仓库弄脏」—— 本仓没有 `.gitattributes`，
`core.autocrlf` 让工作区普遍是 CRLF（docs / tests / research-reports 那些探针**从没碰过**的文件
一样是 `w/crlf`），所以「工作区 CRLF」是这里的常态。真缺陷是**工具改了它不该改的字节**，
以及**判据只看文本**。顺带清掉了历史污染的 stat 噪声（`app/*.py` 12 处 + `web/js-*.js` 6 处），

那是全仓性的行为变更，本轮不擅自做。

**2026-10-25（v1.9.6 附 3）：雷达基线的读-改-写补上跨进程锁 —— 纪律只做了一半的那处。**

的读-改-写只有 `threading.RLock` —— 它是「整份读 → 改几个条目 → 整份写」，两个进程交叉时

**接上远端：**`.github/workflows/ci.yml` 是**唯一一份**
  工作流（单入口：按锁文件安装 → `ci_local --with-exe` → 上传 exe，只在 `windows-latest`）。
  实测三次全绿：run #1（de1dfe2）success 约 7 分钟、run #2（a3af088）success **7 分 35 秒**
  （16:33:11 → 16:40:46 UTC）、run #3（a3ff8b3，v1.4.0 桌面端视觉轮）success，job `gates`
  实测 **467 秒**（run 创建于 2026-10-15 16:22:34 UTC；run 与逐 job 明细都是带 GCM 已有凭据
  走 API 查的，token 不回显、不落临时脚本）。**查 run 时 `?head_sha=` 只认 40 位完整 SHA** ——
  给短号**不报错、只静默返回空的 `workflow_runs`**，极易被误读成"run 还没创建"（实测连查 5 次皆空，
  换 `git rev-parse HEAD` 的全长后一次命中）；别为此去改提交或怀疑推送失败。首跑把本地预演唯一没覆盖的两处都验掉了 ——
  步骤清单里有「装 Playwright 自带 chromium（界面门禁的第三级降级）」且成功（runner 上没有系统
  Edge/Chrome，走的就是这级降级），actions 大版本兼容也一并验证。
  **改 workflow 一律按"它会被真执行"来写** —— 这句话现在有实测背书。
  **2026-10-18 连跑两次**：`fa9bfac`（探针 mtime 契约 + 版本号对账门禁）首跑**红在一条前端 E2E**
  （`tests/test_frontend_e2e.py::test_detail_view_skips_rebuilding_the_hidden_overview`，
  run `39052162314`，报"切回总览时没有补渲染"），同一份代码**本地全绿** —— 根因是用例赌了机器快慢：
  `showOverview` 里 `loadOverview()` 是异步补渲染（等一次 `/api/projects` 回来才重建卡片），
  用例点完立刻读卡片文本，本机 fetch 快就过、runner 上慢一拍就读到旧数据。定性办法是
  **扣住 `/api/projects` 不放**做确定性复现（扣住时旧判据必红、放行后新判据等得到 → 竞态而非产品缺陷，
  隐藏期间不重渲染是有意的优化），修法按惯例改成条件等待（`wait_for_function`）而不是加长睡眠；
  `6421e2d` 复跑 run `39053864773`：`gates` **465 秒 success**、7 个步骤全绿。
  **拉 job 日志**是排 CI 红的第一手段，注意两点：① `.../actions/jobs/{job_id}/logs` 会 302 到 blob 存储，
  **跟随重定向时必须去掉 `Authorization` 头**（`curl -sL` 自动去掉；自己用 urllib 跟跳会撞 401）；
  ② 仓库路径写错一个字母，API 回的是 `404 Not Found` 而**不是**空列表 —— 把它读成 "run 还没创建"
  会白等好几轮（本次就这样绕了一圈，正确路径是 `fengxingxuerong/look`）。
  **2026-10-18 后续两次**：`e547c2c`（CI 记录本身）与 `5350842`（前端分层 5→10 个文件）

   **2026-10-18 v1.7.2 轮两次**：一次性推上去的 10 个提交（v1.5.1→v1.7.1，run `39116037285`）
   与随后的 `00a9a55`（run `39116791745`）、`33155e5`（run `39117335874`）三个 run 都是
   `gates` **success**（最后一个 8 分 02 秒、9 个步骤全绿）。同轮两条可复算的观测：
   ① 探活与推送会**各自独立**成败 —— 本轮 `git ls-remote --heads origin main` 连败 6 轮，

   未跟踪目录时推送本身是安全的（那些东西要影响本地门禁，是另一条线的事）。
   **2026-10-18 v1.7.3 收口轮**：`5c9e804` + `18097e4`（总览截图补「代码变化」标记）推送成功，
