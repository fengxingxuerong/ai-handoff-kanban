# 第八轮竞品复核与用户视角收口（2026-10-22）

> **方法**：在第七轮（2026-10-21，17 组检索 / 33 个候选 README / 7 个重点仓库）的基础上做
> **增量复核**：复核 AyanamiTaskManager、FlowBoard、Pad、veritas-kanban、agent-kanban、
> nimbalyst、kanban-md 的能力矩阵，并补两组公开检索（agent handoff / task claim、kanban）。
> 距上轮仅一天，**未重新抓取全量 GitHub 数据**；星数与推送时间沿用 10-21 快照，不作为今日数据引用。

## 一、结论：没有新的「必须马上追」

- 赛道重心仍是三件事：**会话交接 / 上下文增量**、**任务 claim 与租约**、**验收证据与审核门**。
  第七轮矩阵已经覆盖这些维度，没有出现超出矩阵的新能力形态。
- 本轮补充观察到的 Kaneo（GitHub PR 自动推进任务）、Hermes Kanban（claim/heartbeat/reclaim）
  与 amux（SQLite CAS claim）仍然属于**多 agent 并行执行**场景，与本项目「单人频繁换 agent 的
  项目交接台」切口不同；维持暂缓。
- 第七轮留下的四项按原判：任务 claim/租约 **暂缓**（触发线：同时跑 2+ agent 改同一块板）；
  完成证据 **候选**（与 acceptance / journal / done_at 重叠，等真实需求）；一键写客户端
  MCP 配置 **暂缓**（要改用户其他工具的配置，安全设计成本高于收益）；变更版本史 **不吸收**
  （会让 `projects.json` 持续变胖，单机单人收益有限）。

## 二、本轮转向：真实浏览器从零走查

功能面已经较宽，本轮不扩功能，改为「新用户从空目录打开应用」的真实路径检查。
四处问题都是真实使用中可感知的，且前三处此前没有任何测试能发现：

| # | 用户看到的问题 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 新建任务后，左侧「交接就绪度」仍写「已有任务清单 ✗ / 任务有推进 ✗」，要重新进项目才恢复 | `renderReadiness` 只读 `/api/stats` 的全局快照；详情页保存后只重取单项目 | `GET /api/projects/{pid}` 直接返回 `readiness`（复用 `app/readiness.py`），前端优先用当前详情 |
| 2 | 「今日」面板把项目状态当任务状态：进行中项目里的「待办」任务显示成「进行中」；阻塞任务没有原因；列表卡片键盘打不开 | 模板误用 `project_status`；API 未返回 `blocked_reason`；动态 `div` 缺 `tabindex`/`data-keyact` | 改显任务 `status`、补阻塞原因、补键盘属性；HTTP 与 MCP `kanban_today` 同步 |
| 3 | 打开任务弹窗，状态/优先级/截止/负责 AI 在 1440×900 下位于 y≈870，而可视区底约 785，改状态先得滚动 | 弹窗把「排期与指派」排在验收/代码位置/前置任务之后 | 把排期与指派提到任务描述之后，验收与关联下移 |
| 4 | 首次打开满屏「37 天没记录」「更新于 9 月」，示例项目还指向不存在的本机仓库，触发假告警 | 示例数据写死日期、进度与完成数不自洽、`repo_path` 指向 `D:\work\...` | 示例改为相对今天生成；补已完成任务/截止/依赖；清空 `repo_path` |

附带：项目弹窗的「里程碑」从「交接信息」小节移到独立的「发布节点」，避免把排期字段
误读成交接内容。

## 四、仍不吸收（本轮新增）

- **GitHub Issue/PR 自动推进任务**（Kaneo 路线）：需要常驻 webhook/轮询与 PR 状态机，
  与本地单机、无服务端的形态冲突；现有仓库雷达已经覆盖「代码变了要不要提醒」。
- **claim/heartbeat/reclaim 任务租约**（Hermes / amux / kanban-md）：等真的同时跑两个以上
  agent 改同一块板再议；现在引入会动任务状态机、MCP、界面与过期回收。
- **完成证据字段**：acceptance（怎么算完成）+ journal（做了什么）+ done_at（何时完成）
  已经能表达；先等缺少证据导致接手失败的真实案例，再决定是否加专用字段。
